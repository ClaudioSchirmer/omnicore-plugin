# shared/generated-code-review.md — generated code is a SHORTCUT, not the source of truth

The single home for **what to do when you meet code `omnicore-gen` wrote**. Every skill
routes here — the ones that run the generator and the ones that merely open a project
where it has run, which is most of them. One owner, no drift.

It exists because of a failure that has happened in more than one skill, `implement`
included, and it is always the same sentence: *"the generated code cannot be changed"* —
followed by a workaround built AROUND it. That sentence is wrong.

## The rule, in three lines

1. **Editing generated code is NORMAL.** It is ordinary Go in the dev's repository.
2. **ALWAYS ask the dev first.** The edit is theirs to accept; you propose, they choose.
3. **Once accepted, `adopt` the file** — one command, and the generator keeps the edit
   instead of refusing the next run.

Everything below is that rule with its reasons.

## 1. What the header actually says

Every owned file opens with:

    // Code generated by omnicore-gen. DO NOT EDIT.

**That line is a TOOLING MARKER, not a permission boundary.** It is the Go convention
(`golang.org/s/generatedcode`) that tells linters and analysers to skip the file. It is
not a statement that the code is correct, not a statement that it is the best the
framework can do, and **not a statement that you may not change it**.

Operationally it means one thing: the generator hashes the file, so the next run notices
a hand edit and **stops rather than overwriting your work**. `omnicore-gen adopt <path>`
records the edit; regeneration then keeps it. The mechanism exists because hand edits
were expected from the start.

The code lives in the dev's repository, under their license, compiled into their binary,
on their oncall rotation. **They own it. The generator wrote a first draft.**

## 2. The MUST

**Code the generator produced is REVIEWED like code a person produced — for logic and for
performance — and measured against what the FRAMEWORK offers, not against what the
generator's spec language happens to be able to say.**

The spec language is a subset of the framework, deliberately and permanently: it covers
the shapes that recur, and the framework is larger than any spec language will ever be.
So "the generator does not emit that" is a fact about the GENERATOR. It is never, on its
own, a reason for the service to do the worse thing.

`../shared/query-primitives.md` owns which question to ask the database and
`../shared/capabilities.md` owns what the framework offers. **Both apply to generated
code exactly as they apply to code you write.** They were being read as rules for
hand-written code only, which is how a generated tree ended up doing in Go what the store
does in one pass.

## 3. The workarounds — name them, because they are what is actually happening

Each of these leaves **two answers to one question** in the codebase, and the one that
runs is the worse one:

- **N queries folded in Go.** Calling a generated fact once per case and summing,
  counting or comparing the results in a rule — where one query with the right criteria,
  or one `aggregates` fact, answers it in a single pass. This is the reported case.
- **A parallel hand-written query beside the generated one.** A second repository
  method, a second finder, a second projection asking nearly the same thing, because the
  generated one was "off limits". Now two things must be kept in step, and nothing
  enforces it.
- **Wrapping or shadowing.** A hand-written handler that calls the generated one and
  patches its answer; a type embedding a generated one to override a method.
- **Loading rows to compute a scalar.** `FindAll` + `len()` / a running total / bucketing
  by a key, on the write path — the exact shape `query-primitives.md` exists to stop.
- **Silence.** Noticing the generated code is slower or weaker than the framework allows,
  and saying nothing because "it is generated".

If you are about to write any of these: stop, and go to §4.

## 4. Which edit, and how to offer it

Two rungs, and the only reason to prefer the first is COST, never permission.

**Rung 1 — can the SPEC say it?** Change the spec and regenerate. Cheaper: it survives
every future regeneration and every framework upgrade, and leaves no record to maintain.
Check before assuming it cannot — `omnicore-gen explain keys` lists every key of the
language, `explain rules` the rule and fact vocabulary. A capability added since you last
looked is the common miss.

**Rung 2 — the framework can do it and the spec cannot say it? Then edit the file.** This
is normal and expected. What it requires is an ASK, not a refusal:

  1. **Say what the difference is.** What the generated code does, what the framework
     offers instead, and why it is better — one pass over the table instead of N, one
     query instead of three, an index the store can use, a race the framework's primitive
     closes.
  2. **Show the edit and ask.** Name the file, show the change, and state the cost
     honestly: an adopted file is PINNED — it stops tracking the spec, so every later
     improvement to that emitter (a bug fixed, a guard closed) lands in every other
     project and never there. `upgrade` is where that bill comes due, which is why that
     skill names adopted files before it bumps the pin. Sometimes "leave it, the
     generated version is fine here" is the right answer, and that is the dev's call.
  3. **On acceptance, adopt it — always, in the same breath as the edit:**

         omnicore-gen adopt <path> -why '<what the spec could not express>'

     `adopt` re-hashes the file as it now stands and records the reason in the lock. Skip
     it and the next `generate` refuses the run, and whoever meets that refusal did not
     make the edit. Every later `generate` then prints the file as adopted — *"it no
     longer tracks the spec: emitter improvements will not reach it"* — and `doctor`
     lists it, which is how the edit stays visible instead of becoming a surprise.

**Neither rung fits?** The hook files (`*_manual.go`), written once and never touched
again — `explain ownership` lists them. Nothing to adopt: they are already yours.

## 5. When the generator itself is the gap, say so

If the spec language *should* have been able to express it — the shape is ordinary, other
specs will want it — report it as a generator gap in the same breath as the edit you are
offering. An adopted edit in ten services is a missing key in the language.

## 6. What to say, and what never to say

- **Never:** "this is generated, I cannot change it." It is false, and it is the sentence
  this file exists to delete.
- **Never:** editing an owned file and moving on without `adopt`.
- **Never:** rewriting generated code without asking, either — the ask is the rule, in
  both directions.
- **Say:** what the generated code does, what the framework offers, what it costs to take
  it, the exact commands — then wait for the answer.
